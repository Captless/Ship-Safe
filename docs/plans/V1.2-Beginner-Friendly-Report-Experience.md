# V1.2 — Beginner-Friendly Report Experience

## Status

PLANNED

## Objective

Transform the current V1 scan report from a technically oriented
security/static-analysis report into a beginner-friendly,
decision-oriented experience.

The scanner engine, detection rules, filtering, deduplication,
confidence system, and scoring improvements from V1.1 should remain
intact unless a small backend change is required to support the new
presentation.

The primary goal is NOT to reduce the scanner's technical capability.

The goal is to reduce cognitive overload.

A beginner should be able to open the report and immediately answer:

1. Is my app ready to ship?
2. What should I fix first?
3. Why does it matter?
4. What should I do about it?

Technical users should still be able to access the underlying
technical information when they want it.

==================================================
PRODUCT PRINCIPLE
==================================================

The scanner should feel like:

"Here's what you should fix before launching."

NOT:

"Here's everything our security engine detected."

The primary user is a beginner/intermediate developer who may have
built the application using AI coding tools.

The product should communicate clearly without assuming the user
understands:

- SQL injection
- XSS
- path traversal
- authentication
- authorization
- CSP
- dependency vulnerabilities
- static analysis terminology
- rule IDs
- confidence scores

Technical terminology should still exist, but it should be progressively
revealed rather than presented as the first thing the user sees.

==================================================
CURRENT V1 PROBLEM
==================================================

The current report is technically useful but can be overwhelming.

Examples of the current style include findings such as:

"Potential issue detected: path construction that can escape
the intended directory."

followed by technical explanations, rule IDs, locations,
evidence, remediation information, and multiple occurrences.

The latest report also contains findings such as:

- CODE-005
- CODE-004
- CODE-008
- API-007
- API-002

and aggregated findings containing many locations.

This information is useful for technical inspection but should
not dominate the initial beginner experience.

==================================================
V1.2 DESIGN GOAL
==================================================

Introduce a progressive-disclosure report model:

LEVEL 1 — BEGINNER VIEW

Show:

- Overall readiness
- Ship Score
- Short status
- Number of important issues
- Top issues
- Simple explanations
- Simple recommended actions

LEVEL 2 — FINDING DETAILS

Show:

- Why it matters
- Where it was detected
- What the scanner observed
- Recommended action
- AI Fix Prompt

LEVEL 3 — TECHNICAL DETAILS

Show:

- Technical name
- Rule ID
- Severity
- Confidence
- File
- Line
- Evidence
- Detection metadata

Do NOT remove the underlying information.

Simply move it behind progressive disclosure.

==================================================
TASK 1 — REDESIGN THE REPORT HEADER
==================================================

Replace the current technical-heavy introduction with a simple
readiness summary.

The top of the report should communicate:

BUILD CHECK COMPLETE

Your AI-built project was analyzed.

SHIP SCORE

XX / 100

Then provide a short status based on the score.

Suggested language:

90–100:
"LOOKING GOOD"

75–89:
"ALMOST READY"

50–74:
"REVIEW BEFORE SHIPPING"

25–49:
"DON'T SHIP YET"

0–24:
"HIGH RISK — FIX BEFORE SHIPPING"

The exact score thresholds should reuse the existing scoring
system rather than creating a second scoring system.

Do not claim that the score means the application is secure.

Use wording such as:

"This score is based on the issues detected during this scan."

==================================================
TASK 2 — BEGINNER-FRIENDLY SUMMARY
==================================================

Immediately below the score, provide a short summary.

Example:

"3 things need your attention before you ship."

or:

"Your project looks good overall, but a few things are worth
reviewing before launch."

Do not expose raw rule IDs here.

Do not use technical vulnerability terminology unless necessary.

==================================================
TASK 3 — CREATE HUMAN-FRIENDLY FINDING TITLES
==================================================

Every user-facing finding should have a beginner-friendly title.

The technical rule name should NOT be the primary title.

Examples:

CURRENT:

"Path Traversal"

BETTER:

"Your app may be exposing files"

CURRENT:

"SQL Injection"

BETTER:

"Your database query may be unsafe"

CURRENT:

"Cross-Site Scripting (XSS)"

BETTER:

"User content may be able to run code"

CURRENT:

"Missing Authentication"

BETTER:

"Some parts of your app may not check who's signed in"

CURRENT:

"Hardcoded Secret"

BETTER:

"A sensitive credential may be visible in your app"

The technical name can appear later under:

"Technical details"

Do not invent misleading explanations.

The beginner-friendly title must remain faithful to what the
underlying rule actually detects.

==================================================
TASK 4 — FINDING CARD STRUCTURE
==================================================

Redesign the primary finding card to contain only the information
needed for an initial decision.

Suggested structure:

--------------------------------------------------

[SEVERITY]

BEGINNER-FRIENDLY TITLE

Short one or two sentence explanation.

Why it matters:
One or two simple sentences.

What to do:
One short recommendation.

[How do I fix this?]

--------------------------------------------------

Do not initially display:

- rule ID
- raw evidence
- long remediation text
- technical terminology
- dozens of file locations
- long AI prompts

Those belong inside expandable sections.

==================================================
TASK 5 — THREE-LAYER FINDING DETAIL
==================================================

Each finding should support progressive disclosure.

LEVEL 1:

Example:

🔴 FIX THIS FIRST

Your app may be exposing files.

Your app appears to build file paths using values that may
come from outside the application.

Why it matters:

Someone could potentially use this to access files that
were not intended to be public.

What to do:

Review how the application validates file paths and make sure
user-controlled paths cannot escape the intended directory.

[How do I fix this?]

LEVEL 2:

When expanded, show:

WHY IT WAS FLAGGED

WHAT WE FOUND

WHERE IT WAS FOUND

WHAT TO DO

AI FIX PROMPT

LEVEL 3:

Under:

"Technical details"

show:

Technical name
Rule ID
Severity
Confidence
File
Line
Evidence
Detection metadata

==================================================
TASK 6 — AI FIX PROMPT UX
==================================================

Preserve the existing deterministic AI Fix Prompt functionality.

The scanner must NOT call an external LLM.

The AI Fix Prompt should remain generated from the existing
rule/template system.

Do not show the entire prompt by default.

Use:

[Copy AI Fix Prompt]

Optionally:

[View AI Fix Prompt]

When copied, the user receives the full deterministic prompt.

The prompt should be appropriate for tools such as:

- ChatGPT
- Claude
- Cursor
- OpenCode
- other AI coding assistants

The report must never imply that the scanner itself used AI
to analyze the project unless an actual AI model was used.

==================================================
TASK 7 — SEVERITY LANGUAGE
==================================================

Keep the existing internal severity model.

Do NOT remove:

- Critical
- High
- Medium
- Low
- Informational

However, present severity in beginner-friendly language.

Suggested presentation:

CRITICAL:
"FIX THIS FIRST"

HIGH:
"IMPORTANT"

MEDIUM:
"REVIEW THIS"

LOW:
"GOOD TO KNOW"

INFORMATIONAL:
"OPTIONAL"

The technical severity can still appear under Technical Details.

Do not change the underlying risk classification merely for UX.

==================================================
TASK 8 — PRIORITIZED FINDINGS
==================================================

The main report should prioritize the most important findings.

Do not display every finding as an equally important card.

Suggested structure:

TOP ISSUES

1. Highest-priority finding
2. Second-highest priority finding
3. Third-highest priority finding

Then:

"X more issues found"

[View all issues]

The prioritization must use the existing severity/confidence/
deduplication logic from V1.1.

Do not create a second conflicting prioritization system.

==================================================
TASK 9 — GROUP MULTIPLE LOCATIONS
==================================================

If a finding occurs in many locations, do not display every
location immediately.

Instead show:

"Found in 8 files"

or:

"Found in several places"

Then allow:

[View locations]

Example:

Potential unsafe file handling

Found in 8 files

[View locations]

Expanded:

- src/components/AddKeyModal.ts
- src/components/ApiKeyManager.ts
- src/components/Gallery.ts
- src/components/ImageViewer.ts
- ...

The grouping logic from V1.1 must remain intact.

Do not count duplicate line-level matches as separate user-facing
issues when they represent the same underlying problem.

==================================================
TASK 10 — REMOVE RAW RULE IDS FROM PRIMARY VIEW
==================================================

Do not display:

CODE-005
CODE-004
API-007

in the primary beginner view.

These should remain available under:

Technical details

Example:

Technical details ▾

Rule:
CODE-005

Technical name:
Path Traversal

Confidence:
Medium

Location:
src/example.ts:42

Rule IDs must not be deleted from the underlying finding model.

==================================================
TASK 11 — REMOVE TECHNICAL JARGON FROM PRIMARY COPY
==================================================

Avoid unexplained terms such as:

"taint source"
"sink"
"attack vector"
"directory traversal"
"unsanitized input"
"arbitrary file access"
"unsafe interpolation"

unless they are inside Technical Details.

Instead say:

"Someone may be able to use this input to access files outside
the intended folder."

If a technical term is important, introduce it after the beginner
explanation.

Example:

Technical name:
Path Traversal

rather than:

"Path traversal detected."

==================================================
TASK 12 — CREATE A "WHY IT MATTERS" SECTION
==================================================

Every actionable finding should have a concise:

WHY IT MATTERS

section.

This should answer:

"What could actually happen if I ignore this?"

Examples:

"Someone may be able to access information that should stay private."

"An attacker may be able to manipulate this database query."

"Someone may be able to use this endpoint without proving
who they are."

Do not exaggerate.

Do not claim exploitation is guaranteed when the rule only indicates
a potential issue.

Use cautious language when confidence is not absolute:

"may"
"could"
"appears to"
"might"

==================================================
TASK 13 — CREATE A "WHAT TO DO" SECTION
==================================================

Every actionable finding should have a concise recommended action.

Example:

WHAT TO DO

Review the file path handling and make sure user-provided paths
cannot escape the intended directory.

Keep recommendations short.

Do not provide a long tutorial in the main report.

Detailed remediation can remain available through the AI Fix Prompt
and Technical Details.

==================================================
TASK 14 — INTRODUCE "FIX FIRST / REVIEW / SUGGESTIONS"
==================================================

The report should visually separate findings into three beginner-friendly
categories.

FIX FIRST

Issues that should be addressed before deployment.

REVIEW

Potential issues that should be checked before deployment.

SUGGESTIONS

Lower-priority improvements that are useful but generally not blockers.

These categories are presentation labels.

Do not replace or alter the underlying severity model.

Do not misclassify findings.

==================================================
TASK 15 — LOW / INFORMATIONAL FINDINGS
==================================================

Low and informational findings should not dominate the main report.

Do not delete them.

Place them under:

ADDITIONAL SUGGESTIONS

Example:

"3 lower-priority suggestions"

[Show suggestions]

The user can expand the section.

Informational metadata that is not actionable should not be presented
as a security problem.

For example, simply detecting:

"Dependency manifest detected"

should not be presented as an issue.

If a finding does not represent a meaningful action, consider keeping
it internal or moving it to technical scan metadata.

==================================================
TASK 16 — RAW DETECTIONS VS ACTIONABLE ISSUES
==================================================

Maintain a clear conceptual separation:

RAW DETECTIONS

Everything the scanner identified.

ACTIONABLE ISSUES

Findings that passed the existing filtering, confidence,
deduplication, and prioritization pipeline.

USER PRIORITY

The subset presented prominently in the beginner report.

Do not confuse these counts.

If the scanner internally detects many matches but groups them into
fewer actionable issues, communicate the grouped result.

Example:

65 application files checked

5 important issues found

3 lower-priority suggestions

Do NOT simply display:

42 actionable findings

if the UI only presents five grouped issues without explaining
the relationship.

If raw detection counts are shown, label them clearly.

==================================================
TASK 17 — SIMPLIFY SCAN METADATA
==================================================

The user should see a concise scan summary.

Example:

65 application files checked

1,756 files skipped because they were dependencies, generated
files, build output, or repository metadata.

5 important issues found

3 suggestions

This is enough.

Avoid overwhelming users with internal scanner statistics.

Technical scan statistics can be available under:

"Scan details"

==================================================
TASK 18 — BEGINNER-FRIENDLY EMPTY / GOOD RESULTS
==================================================

Design the report for a clean project too.

If no important findings exist:

BUILD CHECK COMPLETE

YOUR APP LOOKS GOOD

No critical or high-priority issues were detected.

Ship Score:

94 / 100

Before launching, perform your normal manual testing and review.

Do NOT say:

"Your app is secure."

Do NOT say:

"No vulnerabilities exist."

The scanner only reports what it can detect.

==================================================
TASK 19 — NO RESULT SHOULD CREATE UNNECESSARY FEAR
==================================================

Avoid alarmist language.

Do not use copy such as:

"YOUR APP IS VULNERABLE!"

unless the scanner has extremely strong evidence and the wording
is technically justified.

Prefer:

"Your app may have a security issue."

"Review this before shipping."

"Something here deserves attention."

The goal is to help beginners fix problems, not scare them away.

==================================================
TASK 20 — REPORT INFORMATION ARCHITECTURE
==================================================

The preferred high-level structure is:

1. BUILD CHECK COMPLETE

2. SHIP SCORE

3. SIMPLE STATUS

4. SHORT SUMMARY

5. TOP ISSUES

6. ADDITIONAL SUGGESTIONS

7. SCAN DETAILS

8. TECHNICAL DETAILS

Do not make technical details the first thing the user sees.

==================================================
TASK 21 — RESPONSIVE / MOBILE UX
==================================================

The report must remain understandable on small screens.

Finding cards should:

- avoid excessive horizontal content
- wrap long paths
- avoid large tables in the beginner view
- keep primary actions visible
- allow technical details to collapse
- keep AI Fix Prompt controls accessible

Do not redesign the entire application.

Only make changes necessary to support the report experience.

==================================================
TASK 22 — PRESERVE EXISTING SCANNER ENGINE
==================================================

Do not rewrite the scanner.

Preserve:

- safe archive handling
- file exclusion
- confidence system
- deduplication
- severity
- scoring
- rules
- finding model
- performance improvements from V1.1

Only introduce backend changes if required to expose the
additional presentation metadata.

==================================================
TASK 23 — PRESERVE DETERMINISTIC OPERATION
==================================================

DO NOT:

- add OpenAI
- add Claude
- add Gemini
- add OpenRouter
- add another LLM API
- add external AI inference
- add token-based scan analysis

The scanner must remain deterministic.

AI-related functionality in this version is limited to:

1. AI-oriented product language.
2. Deterministic AI Fix Prompts.
3. Copyable prompts for external coding assistants.

# V1.2 — Implementation Clarifications

This section resolves the implementation questions identified before
V1.2 implementation.

These decisions are authoritative for this implementation.

==================================================
1. COPY MAPPING
==================================================

Prefer extending the existing rule definitions / finding metadata
structure if the current architecture already provides an appropriate
place for user-facing rule metadata.

Do NOT duplicate rule-specific copy across frontend components.

The preferred conceptual structure is:

Rule / Finding
├── rule_id
├── technical_name
├── severity
├── detection logic
├── beginner_title
├── short_explanation
├── why_it_matters
├── recommended_action
└── existing remediation / AI fix prompt

However, do not force this structure if it conflicts with the
existing architecture.

If the existing rule definitions are not an appropriate place for
presentation metadata, create a small centralized messaging module
alongside the existing scanner/rule modules.

Preferred fallback:

scanner/messaging.py

The messaging layer must own the mapping:

rule/category
→ beginner title
→ short explanation
→ why it matters
→ recommended action
→ technical name

The frontend must NOT contain large rule-specific mappings.

The frontend should consume structured presentation data.

Do not create an unnecessarily complex messaging framework.

Reuse the existing deterministic AI Fix Prompt/remediation system
where possible.

Do not introduce an external LLM or AI API.

==================================================
2. BACKEND VS FRONTEND REPORT RENDERING
==================================================

The frontend `renderResults` implementation is the PRIMARY
V1.2 user-facing report renderer.

V1.2 introduces an interactive beginner-friendly experience
including:

- expandable finding details
- technical details
- grouped locations
- AI Fix Prompt controls
- copy feedback
- accessibility interactions
- responsive behavior

These responsibilities belong primarily in the frontend.

The backend `_render_report` implementation must NOT become a
second competing implementation of the V1.2 beginner UX.

If `_render_report` is currently required by existing functionality,
preserve it.

Modify it only as necessary to:

- preserve compatibility
- expose structured data
- maintain existing behavior

Do not create two independent versions of the V1.2 presentation.

The intended architecture is:

scanner/backend
    ↓
structured scan result
    ↓
frontend renderResults()
    ↓
V1.2 interactive beginner report

Backend remains authoritative for:

- detection
- severity
- confidence
- filtering
- deduplication
- grouping
- prioritization
- scoring
- locations
- technical metadata
- deterministic AI Fix Prompts

Frontend remains responsible for:

- beginner-facing presentation
- finding cards
- progressive disclosure
- expandable sections
- technical detail visibility
- AI Fix Prompt controls
- copy interactions
- accessibility
- responsive presentation

The frontend MUST NOT independently calculate security severity,
risk, grouping, or score.

==================================================
3. CLEAN PROJECT COPY

Use the following exact primary copy when there are zero Critical,
High, and Medium actionable findings:

BUILD CHECK COMPLETE

YOUR APP LOOKS GOOD

No critical or high-priority issues were detected.

Ship Score:
{score} / 100

Before launching, perform your normal manual testing and review.

The score value must use the existing scoring system.

The report MUST NOT claim:

- "Your app is secure."
- "No vulnerabilities exist."
- "You're completely safe."
- "Ready to deploy with no risk."

The scanner only reports issues it can detect.

If Low or Informational suggestions exist, they may still appear
under the lower-priority Suggestions section.

==================================================
4. ACCESSIBILITY
==================================================

Severity MUST NOT be communicated through color alone.

Every severity indicator must contain visible text.

Use beginner-friendly severity labels:

Critical — Fix this first
High — Important
Medium — Review this
Low — Good to know
Informational — Optional

Icons may supplement the text but must not replace it.

Expandable sections MUST use semantic buttons.

Do NOT implement expandable sections using clickable `<div>`
elements.

Expandable controls should use:

- `<button type="button">`
- `aria-expanded`
- `aria-controls`
- unique controlled-content IDs

Keyboard users must be able to:

- Tab to expandable controls
- Activate with Enter
- Activate with Space

Focus behavior must remain predictable when sections expand
or collapse.

Copy buttons must provide visible feedback.

Example:

Before:
"Copy AI Fix Prompt"

After successful copy:
"Copied!"

Do not communicate the copied state only through color.

Buttons must have meaningful accessible names.

Avoid icon-only controls unless they have an appropriate
accessible label.

Finding cards should maintain a logical heading hierarchy.

Long file paths must wrap rather than force horizontal scrolling
in the primary report.

The report must remain usable on mobile.

Do NOT introduce snapshot testing merely for this feature.

Use the existing project testing infrastructure wherever possible.

- rule → beginner title

project
→ scanning
→ filtering

→ grouping
→ prioritization

At minimum cover:

- clean project
- Critical finding
- High finding
- Medium finding
- Low finding
- Informational finding
- duplicate findings
- finding with many locations
- ignored/vendor/generated files

V1.2 should not silently change scanner detection or scoring

--------------------------------------------------

--------------------------------------------------

The backend must provide sufficient structured data for the frontend
to render:

- Ship Score
- overall status
- summary counts
- prioritized findings
- beginner presentation copy
- severity
- technical metadata
- grouped locations
- deterministic AI Fix Prompt

Conceptually, a finding should expose information similar to:

finding
├── id
├── severity
├── confidence
├── beginner
│   ├── title
│   ├── summary
│   ├── why_it_matters
│   └── recommended_action

│   ├── name
│   ├── rule_id

│   └── locations

Adapt it to the existing project's data model.

The backend remains authoritative.

The frontend must not reconstruct scanner findings by parsing

The frontend must not calculate severity, risk, grouping,

==================================================
7. ARCHITECTURAL CONSTRAINTS
==================================================

V1.2 is primarily a report UX and information-architecture
