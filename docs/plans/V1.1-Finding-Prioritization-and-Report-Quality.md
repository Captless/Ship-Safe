# V1.1 — Finding Prioritization and Report Quality

## Status
PLANNED

## Objective
Reduce scanner noise, improve finding accuracy and prioritization,
and simplify the user-facing scan report.

## Scope
- File analysis scope
- Vendor/generated file exclusion
- Finding confidence filtering
- Finding deduplication
- Finding prioritization
- Score refinement
- Simplified report
- Regression tests

V1 REPORT QUALITY + FINDING NOISE REDUCTION

We have completed the first V1 implementation and tested the scanner.

The current scanner is producing too many findings and the report is overwhelming for the intended user: beginner/intermediate developers who build applications using AI coding tools.

The goal of this task is NOT to add more detection rules.

The goal is to make the scanner substantially more accurate, focused, and actionable.

==================================================
PRIMARY PRODUCT PRINCIPLE
==================================================

The scanner should prioritize:

"Show me the small number of issues I actually need to care about before shipping."

It should NOT behave like a raw SAST output dump.

Internal detection can remain broad, but the user-facing report must prioritize high-confidence, actionable findings.

We want:

FEWER FINDINGS
+
HIGHER SIGNAL
+
BETTER GROUPING
+
SIMPLER REPORT

Do not solve this by simply hiding real critical issues.

==================================================
PROBLEM OBSERVED IN V1
==================================================

The current scanner is reporting findings from files that should not normally be analyzed as application source.

Examples observed:

node_modules/
.git/
dist/
build/
generated files
source maps
dependency package files

Examples include findings such as SQL injection being reported inside:

node_modules/tailwindcss/...
node_modules/jiti/...
node_modules/object-hash/...

and path traversal being reported inside:

.git/hooks/...

These are not useful as normal application findings for the target user.

The scanner is therefore producing significant false-positive/noise behavior.

==================================================
TASK 1 — CREATE A FILE SCOPE / ANALYSIS POLICY
==================================================

Implement a centralized file-analysis policy.

Do NOT scatter exclusion logic across individual rules.

Create one authoritative mechanism responsible for determining whether a file should be analyzed.

By default, exclude:

node_modules/
vendor/
.git/
.svn/
.hg/
dist/
build/
out/
.next/
.nuxt/
.cache/
coverage/
tmp/
temp/
target/
__pycache__/
.pytest_cache/

Also exclude generated/minified artifacts where appropriate:

*.min.js
*.min.css
*.map

and other clearly generated artifacts.

The exclusion mechanism must:

1. Normalize paths before checking.
2. Handle Windows and Unix separators.
3. Prevent path traversal during extraction.
4. Be case-aware according to the filesystem-independent project policy.
5. Be reusable by every scanner rule.
6. Be covered by tests.

==================================================
TASK 2 — DISTINGUISH SOURCE FROM VENDOR CODE
==================================================

The scanner must distinguish between:

USER APPLICATION CODE

and

THIRD-PARTY / GENERATED / BUILD ARTIFACTS.

Default behavior:

Analyze:
- src/
- app/
- pages/
- components/
- server/
- api/
- routes/
- lib/
- services/
- functions/
- backend/
- frontend/
- project root configuration

when those directories/files exist.

Do not assume every project uses these exact directories.

Use the project's actual structure.

The scanner must remain framework-agnostic.

==================================================
TASK 3 — FINDING CONFIDENCE GATING
==================================================

Every finding should have:

severity
confidence
category
rule_id
file
line

Use confidence as a filtering mechanism.

User-facing findings should generally require:

HIGH confidence

or

MEDIUM confidence + meaningful evidence

Low-confidence findings should not automatically appear as major findings.

They may be included under:

"Additional observations"

if useful.

Never promote weak pattern matches to Critical/High without sufficient evidence.

==================================================
TASK 4 — FINDING DEDUPLICATION
==================================================

Implement centralized finding deduplication.

Multiple matches representing the same underlying problem should be grouped.

For example:

Instead of:

5 separate SQL injection cards

show:

Potential SQL injection
5 locations

with expandable locations.

Deduplication should consider:

rule_id
normalized message/category
file group
underlying issue type

Do not blindly merge unrelated findings.

==================================================
TASK 5 — FINDING PRIORITIZATION
==================================================

Create a user-facing prioritization layer.

Suggested priority:

P0:
Critical + high confidence

P1:
High + high/medium confidence

P2:
Medium + meaningful confidence

P3:
Low / informational

The report should primarily show P0-P2.

P3 should be collapsed by default.

==================================================
TASK 6 — SIMPLIFY USER-FACING REPORT
==================================================

Redesign the report so it is decision-oriented.

The top of the report should contain:

BUILD CHECK COMPLETE

Project summary

SHIP SCORE

Critical count
High count
Medium count
Low/Info count

Then provide a short status message.

Examples:

90-100:
"LOOKING GOOD"

75-89:
"ALMOST READY"

50-74:
"REVIEW BEFORE SHIPPING"

25-49:
"DON'T SHIP YET"

0-24:
"HIGH RISK — FIX BEFORE SHIPPING"

Do not claim that a score means the application is secure.

The score must clearly remain a heuristic based on detected issues.

==================================================
TASK 7 — LIMIT DEFAULT VISIBLE FINDINGS
==================================================

Do not overwhelm the user with dozens of cards.

Default visible report:

Critical
High
Medium

Low/Informational findings should be collapsed.

Example:

"7 additional low-priority observations"

[Show details]

If there are many findings, show the most important findings first.

Suggested default:

up to 5 most important findings prominently

followed by:

"View all findings"

Do not discard findings internally.

==================================================
TASK 8 — GROUP RELATED FINDINGS
==================================================

If the same rule detects the same issue across many locations:

Group them.

Example:

BAD:

SQL Injection
file A

SQL Injection
file B

SQL Injection
file C

SQL Injection
file D

GOOD:

Potential SQL Injection

4 locations detected

[Expand locations]

The finding detail can show:

file A
file B
file C
file D

==================================================
TASK 9 — SIMPLIFY FINDING LANGUAGE
==================================================

Current findings are too verbose.

Each primary finding should contain only:

TITLE

LOCATION

WHAT WE FOUND

WHY IT MATTERS

WHAT TO DO

OPTIONAL:
AI FIX PROMPT

Keep explanations concise.

Example:

TITLE:
Exposed API credential

WHAT WE FOUND:
A credential appears to be embedded in client-side code.

WHY IT MATTERS:
Users may be able to retrieve it from the deployed application.

WHAT TO DO:
Move the credential to a server-side environment variable.

Do not write long security essays.

==================================================
TASK 10 — KEEP AI FIX PROMPTS
==================================================

Do not remove the existing AI fix prompt functionality.

However:

AI fix prompts should only appear when the user expands a finding.

Do not show large AI prompts directly in the main report.

The user should see:

[Generate / Copy AI Fix Prompt]

or

[Show AI Fix Prompt]

The prompt itself must remain deterministic/static and must NOT require an external LLM API.

==================================================
TASK 11 — AI-NATIVE LANGUAGE WITHOUT AI API COST
==================================================

Preserve the product positioning around AI-assisted development.

Use deterministic copy such as:

"Your AI-built project was analyzed."

"AI can build fast. It can also miss things."

"Here's what your build should review before shipping."

"Your AI-built app has a few things worth checking."

Do NOT imply that an LLM actually analyzed the source unless an LLM was actually used.

Do NOT add an LLM dependency.

Do NOT call OpenAI, Claude, Gemini, OpenRouter, or any external AI API.

The scanner must remain fully deterministic and locally executable.

==================================================
TASK 12 — SCORE SHOULD REFLECT ACTIONABLE FINDINGS
==================================================

Review the current scoring logic.

Do not allow hundreds of low-value findings to destroy the score.

Critical/high-confidence issues should have the strongest impact.

Low/informational observations should have little or no impact.

Duplicate findings must not multiply the penalty unfairly.

A third-party dependency file that is excluded from analysis must contribute zero findings.

Add tests covering:

clean project
critical issue
multiple duplicate issues
many low-priority observations
vendor-only matches
generated-file matches

==================================================
TASK 13 — DO NOT SILENTLY HIDE SECURITY ISSUES
==================================================

Important:

This is NOT permission to simply hide findings to make the report look better.

The system should separate:

DETECTED FINDINGS

from

USER-FACING PRIORITIZED FINDINGS.

All detections can remain available internally/debug mode.

The normal report should present the highest-value findings first.

Provide an optional:

"View all findings"

section.

==================================================
TASK 14 — ADD SCAN SUMMARY
==================================================

The report should include a concise summary such as:

BUILD CHECK COMPLETE

137 files analyzed
92 application files
45 ignored/generated/vendor files

8 actionable findings

1 Critical
2 High
5 Medium

12 low-priority observations hidden

SHIP SCORE
64 / 100

REVIEW BEFORE SHIPPING

This gives users confidence that the scanner actually analyzed the project.

==================================================
TASK 15 — TESTING
==================================================

Add or update automated tests for:

1. node_modules is excluded
2. .git is excluded
3. dist is excluded
4. build is excluded
5. source maps are excluded
6. generated/minified files are excluded
7. application source is analyzed
8. duplicate findings are grouped
9. low-confidence findings are deprioritized
10. critical findings remain visible
11. score is not inflated by duplicate findings
12. score is not destroyed by informational findings
13. Windows paths work
14. Unix paths work
15. malicious archive paths remain safely rejected

Create fixture projects where appropriate.

==================================================
TASK 16 — DO NOT REWRITE THE WHOLE PROJECT
==================================================

Do not rebuild the application from scratch.

Inspect the existing architecture first.

Reuse existing:

- finding model
- scanner engine
- rules
- scoring system
- report generation
- frontend components

Refactor only where necessary.

The preferred architecture is:

scanner rules
      ↓
raw findings
      ↓
scope filtering
      ↓
confidence filtering
      ↓
deduplication/grouping
      ↓
prioritization
      ↓
scoring
      ↓
user-facing report

Keep these responsibilities separated.

==================================================
TASK 17 — PRESERVE EXISTING SECURITY
==================================================

Do not weaken:

- archive validation
- path traversal protection
- upload limits
- temporary file cleanup
- secret redaction
- safe static analysis
- non-execution of uploaded application code

The scanner must NEVER execute uploaded application code.

Instead, the user should receive something similar to:

----------------------------------------

BUILD CHECK COMPLETE

SHIP SCORE

The report should feel like:

"Here are the things you should fix before launching."

NOT:

"Here are 143 things the scanner found."

==================================================
IMPLEMENTATION PROCESS
==================================================

Before changing code:

1. Inspect the current scanner architecture.
2. Identify where file discovery occurs.
3. Identify where rules receive files.
4. Identify the finding model.
5. Identify scoring.
6. Identify report rendering.
7. Produce a concise implementation plan.

Then implement the changes.

Do not add unrelated features.

Do not add an LLM.

Do not add external API calls.

Do not add billing/auth/GitHub integration.

This task is strictly:

REDUCE SCANNER NOISE
+
IMPROVE FINDING ACCURACY/Prioritization
+
SIMPLIFY REPORT
+
PRESERVE REAL SECURITY FINDINGS.

After implementation, run the complete test suite and report:

- tests passed
- tests failed
- files changed
- number of findings before/after on existing fixtures
- any remaining known false positives
