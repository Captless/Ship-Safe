# V1.3 — Terminal-Style Scan Progress

## Objective

Replace the current checklist-style scan progress tracker with a simple
terminal-inspired live progress experience.

The current checklist approach is unreliable because fast backend phases
can be skipped by frontend polling. The new UI must not depend on every
phase being observed.

## Important

The CURRENT LOCAL WORKING DIRECTORY is the source of truth.

Before implementation:

- inspect the current codebase
- inspect the existing scan progress implementation
- inspect frontend progress rendering
- inspect scanner progress state
- inspect existing tests
- inspect current V1.2.x completion flow

Do NOT use the remote GitHub repository as the implementation source.

Do NOT create duplicate progress systems.

## Behavior

### Discovery

Show the real discovered-file count.

Do not show a fake percentage because the final total is unknown.

### Filtering

If observed, show:

> Filtering files
  84 files selected

If the phase is too fast to observe, that's fine.

### Scanning

When `current` and `total` are available, show a real progress bar.

Display:

- percentage
- current / total
- current file when available
- findings found when available

Never fabricate progress.

### Reviewing / Report

Show the current operation when observed.

Do not add artificial delays just to make phases visible.

### Completion

Keep the existing flow:

Scan → Scan Complete → Review Report → Full Report

Do NOT automatically display the full report.

### Errors

Preserve the existing error behavior.

---

## UI Requirements

The new design should:

- feel like a modern developer tool
- be terminal-inspired but beginner-friendly
- use existing Ship Safe styling
- work on mobile
- support reduced motion
- avoid excessive animation
- keep activity history short
- never log every file
- never expose raw debug/scanner logs

The terminal aesthetic should be subtle, not a fake hacker console.

---

## Implementation Constraints

Prefer modifying the existing progress implementation.

Remove obsolete checklist-specific code after verifying its usages.

Do NOT introduce:

- WebSockets
- SSE
- Redis
- external realtime services
- artificial delays
- fake progress
- unnecessary dependencies
- duplicate progress components

Keep the existing scanner, polling, rules, scoring and report generation
unless codebase inspection identifies a concrete bug requiring a change.
