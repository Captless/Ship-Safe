# Ship Safe v1.5 — Evidence-Based Scan Semantics

## Overview
Evolved Ship Safe's scan semantics to be evidence-based, stopping misleading claims like "Payment handling looks reasonable" when no payment code exists.

## Core Changes

### Evidence Model
- **EvidenceState enum**: `NOT_OBSERVED`, `OBSERVED`, `CHECKED_CLEAN`, `LIMITED`, `NEEDS_REVIEW`
- **CategoryEvidence**: state, signals[], checks_run[], checks_passed[], findings[], confidence
- NOT_OBSERVED means "insufficient evidence to assess" — NOT "functionality definitely does not exist"

### Presence Detection (reuses Rule infrastructure)
Added presence-signal rules (`is_presence_signal=True`, `evidence_signal="..."`) for 5 categories:
- **payments**: PAY-100 (Stripe/PayPal/... SDK), PAY-101 (checkout/payment keywords)
- **auth**: AUTH-100 (login/signin/register), AUTH-101 (jwt/session/middleware)
- **database**: DB-100 (ORM/DB client), DB-101 (SQL statements)
- **api**: API-100 (HTTP route decorators)
- **deployment**: DEPLOY-100 (config files), DEPLOY-101 (server entry points)

Generic categories (secrets, git, config, dangerous-code, dependencies) have NO presence rules — existing behavior untouched.

### Scan Flow (engine.py)
1. Run presence rules → collect signals per category
2. Run all check rules (always, preserves coverage)
3. Compute state per evidence-aware category:
   - findings → NEEDS_REVIEW
   - no signals → NOT_OBSERVED
   - signals but no checks ran → OBSERVED
   - partial checks → LIMITED
   - all applicable checks clean → CHECKED_CLEAN
4. `passed` excludes NOT_OBSERVED/OBSERVED/LIMITED categories' rules
5. `derive_readiness(score, evidence, findings)`:
   - critical finding → NOT_READY_TO_SHIP
   - high/medium finding → REVIEW_BEFORE_SHIPPING
   - OBSERVED/LIMITED present → LIMITED_CONFIDENCE
   - else score ≥ 90 → LOOKS_READY_TO_SHIP else REVIEW_BEFORE_SHIPPING

### Messaging
- No "verified secure" wording anywhere
- CHECKED_CLEAN: "No issues found in checks performed. Does not guarantee X is secure."
- Beginner-friendly evidence messages per state

### UI
- Backend report: "What we assessed" evidence rows (state + signals)
- Frontend: readiness badge, clickable evidence chips with advanced details
- Passed chips only for CHECKED_CLEAN categories + generic rules

## Tests
All 80 existing tests pass. Behavior validated against scenarios:
- Payment project with Stripe, no routes → LOOKS_READY_TO_SHIP
- Auth routes without middleware → NEEDS_REVIEW (AUTH-001 fires)
- Generic project → LIMITED_CONFIDENCE (api detected, partial coverage)
- Critical secret → NOT_READY_TO_SHIP
