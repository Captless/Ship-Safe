# V1.2.1 — Real-Time Scan Progress Experience

## Status

PLANNED

## Implementation Priority

HIGH

## Objective

Replace the current fake/looping scan progress experience with a
real-time, backend-driven progress system.

The user should see what Ship Safe is actually doing while the ZIP
project is being analyzed.

The progress experience should include:

- Real scan phases
- Real progress tracking
- Determinate progress where actual totals are known
- Indeterminate progress where totals are not known
- Current file being analyzed
- Files discovered
- Files skipped
- Application files selected for analysis
- Files analyzed
- Findings discovered so far
- Completed/active/pending phase tracker
- Clear completion state
- Clear failure state

The system MUST NOT simulate progress with a timer.

The system MUST NOT invent percentages.

The system MUST NOT continuously rotate arbitrary status messages.

The backend scanner state must be the source of truth.

Current backend scan flow is approximately:

POST /api/scans
    ↓
_save_upload()
    ↓
safe_extract_zip()
    ↓
iter_text_files()
    ↓
scan_root()
    ↓
store completed result
    ↓

The current backend creates/stores the scan result after the scan
has already completed.

The current frontend contains a hard-coded PROGRESS_STAGES array
and a timer-based progress cycle.

The current frontend also contains polling support, but polling
currently only becomes useful after a scan ID exists and the
backend has a completed result.

Therefore, V1.2.1 requires a real asynchronous/background scan
lifecycle before intermediate progress can be delivered.

Do NOT preserve the existing fake timer as the primary progress
mechanism.

TASK 3 — CREATE A REAL ASYNCHRONOUS SCAN LIFECYCLE
==================================================

The current POST /api/scans performs the entire scan before returning.

Change this behavior so that the backend can:

1. Accept the upload.
2. Create a scan ID.
3. Create an initial scan state.
4. Start the scan work without blocking the client until completion.
5. Allow the frontend to retrieve progress.
6. Update progress during the scan.
7. Store the final result.
8. Mark the scan complete.
9. Clean up temporary resources safely.

The implementation should use the existing project's lightweight
Python/FastAPI architecture.

Do NOT introduce:

- Redis
- Celery
- RabbitMQ
- external queues
- databases solely for progress
- WebSocket infrastructure
- external services

A lightweight in-process background execution approach is preferred
if it is safe and compatible with the current project.

Inspect the existing server/concurrency model before selecting the
implementation.
