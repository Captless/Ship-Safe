# V1.2.1 — Real-Time Scan Progress Experience

## Status

PLANNED

## Objective

Replace the current looping/fake scanning spinner with a real-time,
phase-based scan progress experience.

The user should be able to see:

1. What the scanner is currently doing.
2. Which phase of the scan is active.
3. How much work has been completed.
4. How many files have been discovered.
5. How many files are being analyzed.
6. Which file is currently being processed when appropriate.
7. How many findings have been discovered so far.
8. Which phases have already completed.
9. When the scan is complete.
10. When an error occurs.

The progress UI must reflect actual scanner state.

DO NOT implement a fake timer-based percentage.

DO NOT continuously cycle arbitrary status messages to simulate
activity.

The progress system must be driven by real backend scan events.

==================================================
PRODUCT PRINCIPLE
==================================================

The current scanner uses a looping spinner/status message while the
backend performs the scan.

This creates the perception that the application does not know what
is happening.

V1.2.1 should make the scanner feel transparent and trustworthy.

The experience should communicate:

"We know what we're doing, and here's where we are."

The user should never need to wonder:

"Is it stuck?"

"Is it still scanning?"

"How much longer?"

"Did anything actually happen?"

The progress UI should be calm, informative, and beginner-friendly.

==================================================
CORE REQUIREMENT
==================================================

Implement REAL progress tracking.

The frontend must receive progress information from the backend
while the scan is running.

The backend must emit progress events as meaningful scan milestones
occur.

The frontend must render those events.

Do not estimate progress using elapsed time.

Do not increment a fake percentage every N milliseconds.

Do not cycle fake "Scanning..." messages indefinitely.

ARCHITECTURAL MODEL
==================================================

The intended architecture is:

Browser
    │
    │ Upload ZIP
    ▼
Backend
    │
    ├── create scan
    │
    └── execute scan
           │
           ├── progress event
           ├── progress event
           ├── progress event
           ├── progress event
           └── completion event
                    │
                    ▼
Browser receives events
    │
    ▼
Progress UI updates
    │
    ▼
Scan complete
    │
    ▼
Results report

Use the simplest architecture compatible with the existing project.

The existing backend uses Python's standard-library HTTP server
architecture.

Before implementation, inspect the current scan execution model.

Prefer Server-Sent Events (SSE) if the existing architecture can
support it cleanly without introducing unnecessary dependencies.

If SSE conflicts with the current architecture, use lightweight
polling with a scan ID and structured progress state.

Do NOT introduce WebSockets unless the existing architecture makes
them clearly necessary.

Do NOT introduce external services.

Do NOT introduce new infrastructure merely for progress tracking.

==================================================

Use approximately these phases:

2. PREPARING
3. DISCOVERING
4. FILTERING
5. SCANNING

==================================================
TASK 3 — PHASE DEFINITIONS
==================================================

### UPLOADING

User-facing message:

"Uploading your project"

Progress may use actual upload progress if available.

If upload progress is already provided by the browser/network layer,
use it.

Do not fabricate upload percentages.

--------------------------------------------------

### PREPARING

User-facing message:

"Preparing your project"

Purpose:

- create scan workspace
- prepare extraction
- validate uploaded archive

--------------------------------------------------

### DISCOVERING

User-facing message:

"Discovering project files"

Show:

"1,821 files discovered"

when the count becomes available.

This phase may use indeterminate progress until discovery completes.

--------------------------------------------------

### FILTERING

User-facing message:

"Preparing files for analysis"

Show actual values when available:

"1,756 files skipped"

"65 application files selected"

--------------------------------------------------

### SCANNING

User-facing message:

"Checking your application"

This is the primary determinate progress phase.

When possible, show:

"44 / 65 files"

and:

"Currently checking:"
"src/components/Gallery.ts"

The percentage must be calculated from actual:

current / total

and NOT from elapsed time.

--------------------------------------------------

### REVIEWING

User-facing message:

"Reviewing findings"

Use this phase for:

- deduplication
- grouping
- prioritization
- result organization

If the backend does not have measurable sub-progress for this phase,
use an indeterminate progress indicator.

Do NOT invent a percentage.

--------------------------------------------------

### BUILDING_REPORT

User-facing message:

"Preparing your report"

Use an indeterminate progress indicator unless actual measurable
progress exists.

--------------------------------------------------

### COMPLETE

User-facing message:

"Scan complete"

Show:

✓ Scan complete

Then transition to the V1.2 beginner-friendly results report.

==================================================
TASK 5 — DETERMINATE VS INDETERMINATE PROGRESS
==================================================

Use determinate progress ONLY when actual progress can be measured.

Example:

44 / 65 files

████████████████░░░░

This may display a percentage.

Use indeterminate progress when the total cannot reasonably be
known.

Example:

Reviewing findings
━━━━━━━━━━━━━━●━━━━━━

Do NOT display:

83%

unless the backend can actually support that number.

A visually animated progress bar is acceptable for indeterminate
states, but it must not imply a specific completion percentage.

==================================================
TASK 13 — FAST SCANS
==================================================

Do not display a large progress UI for extremely fast scans.

Use an adaptive strategy.

Suggested behavior:

If the operation completes very quickly:

show a minimal loading state.

If the scan continues long enough for progress to be useful:

show the full progress interface.

Do not flash the full progress screen for a scan that completes
almost immediately.

The exact threshold should be determined from the existing frontend
behavior and tested rather than arbitrarily hardcoded if possible.

==================================================
TASK 14 — COMPLETION TRANSITION
==================================================

When the backend emits completion:

Show briefly:

✓ Scan complete

Then transition to the V1.2 beginner-friendly report.

Do not leave the user staring at a completed progress bar.

The completion transition should feel deliberate but fast.

Avoid unnecessary animations that delay access to the results.

==================================================
TASK 15 — ERROR STATE
==================================================

If scanning fails, stop the progress animation.

Display:

SCAN COULD NOT BE COMPLETED

A short explanation.

Example:

"We couldn't finish analyzing this project."

Then provide:

[Try Again]

If an actionable error reason is available, show a beginner-friendly
explanation.

Do not expose raw Python stack traces in the primary UI.

Technical error details may remain available through an advanced
section or developer logging.

==================================================
TASK 16 — CONNECTION INTERRUPTION
==================================================

If using SSE:

Handle temporary connection interruptions gracefully.

The frontend should not immediately display:

"Scan failed"

merely because the event stream temporarily disconnects.

Attempt to reconnect when appropriate.

If the backend scan is still running, resume receiving progress.

If using polling:

Continue polling while the scan is active.

Stop polling when:

- complete
- failed
- cancelled
- expired

Avoid aggressive polling intervals.
